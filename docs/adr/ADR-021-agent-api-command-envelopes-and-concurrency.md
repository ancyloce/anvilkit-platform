# ADR-021: Agent API Command Envelopes, Authorization Carrier, and Concurrency

| Item | Decision |
| --- | --- |
| Status | Accepted |
| Date | 2026-08-18 |
| Scope | P0-Kernel and P0-Integration |
| Related ADRs | ADR-016, ADR-018, ADR-020 |

## Context

Some current Agent API write operations accept a complete resource document. That allows callers to submit fields that must be owned by the server. For example, creating a run can accept a complete AgentRun, while issuing an Apply Authorization can accept issuer-owned identifiers, times, digests, and key data.

This confuses client intent with server fact, expands the privilege and signing attack surface, and leaves idempotency, optimistic concurrency, bodyless request digests, expiry, errors, and stream recovery insufficiently defined.

AnvilKit is greenfield. The API will be refactored directly. No old request shapes, compatibility endpoints, fallback parsers, or dual behavior will be retained.

## Decision

### 1. Separate command requests from resource representations

Every write operation uses a dedicated command request. A command contains only intent the caller is authorized to declare. Resource identifiers, actor identity, issuer identity, timestamps, policy/BOM digests, resource state, and signatures are resolved or generated by Agent Service.

#### CreateAgentRunRequest

The caller may declare:

- Agent Definition reference;
- TargetReference, including the required `projectId`;
- user input or authorized artifact references;
- optional client labels from an allowlist.

The caller may not declare:

- `runId`, `workspaceId`, actor, or subject;
- initial state or resource revision;
- final policy, BOM, or definition digest bindings;
- created/updated timestamps, sequence, or signature fields.

`workspaceId` comes from the route and authenticated context. Actor identity comes from authentication. Agent Service verifies that the target project belongs to the workspace.

#### IssueApplyAuthorizationRequest

The caller may declare:

- `runId` and the artifact or patch to apply;
- action and target;
- base revision;
- the satisfied approval reference;
- the expected AgentRun revision.

Agent Service derives or generates:

- authorization ID, issuer, subject, and audience;
- `issuedAt`, `notBefore`, and `expiresAt`;
- key ID and signing algorithm;
- final policy, BOM, definition, artifact, and target digest bindings;
- replay-protection data.

### 2. Use compact JWS as the Apply Authorization carrier

Following ADR-016:

- use compact JWS;
- use EdDSA with Ed25519;
- allow only `alg`, `kid`, and `typ` in the protected header;
- use the JCS-canonicalized ApplyAuthorization JSON as the payload;
- use `anvilkit-apply-authorization+jws` as `typ`.

The response shape is:

```text
IssuedApplyAuthorization {
  authorization: ApplyAuthorization,
  compactJws: string
}
```

The `authorization` value must be byte-equivalent to the decoded JWS payload after canonicalization. Callers must not modify or recombine the two values.

### 3. Use standard If-Match optimistic concurrency

Every command that changes an existing AgentRun requires a strong ETag:

```http
If-Match: "run:<runId>:<resourceRevision>"
```

- read and state-changing responses return the corresponding `ETag`;
- a missing required `If-Match` returns `428 Precondition Required`;
- a stale value returns `412 Precondition Failed`;
- a valid revision with an invalid business transition returns `409 Conflict`;
- no private expected-revision header is added.

### 4. Define idempotency and creation responses

- every command that creates a resource or external side effect requires `Idempotency-Key`;
- the first successful AgentRun creation returns `201 Created`, `Location`, and `ETag`;
- replaying the same authenticated subject, route, command digest, and key returns the recorded result with `Idempotency-Replayed: true`;
- reusing a key with a different command digest returns `409 IDEMPOTENCY_KEY_REUSED`;
- key isolation includes workspace, authenticated subject, HTTP method, and normalized route.

### 5. Canonicalize bodyless write requests as an empty object

For cancel, retry, discard, and other commands with no business body, the canonical body is the UTF-8 JCS empty object:

```json
{}
```

Implementations must not choose independently among empty bytes, `null`, and `{}`. Cross-language fixtures cover bodyless requests, explicit `{}`, whitespace, and content-type behavior.

### 6. Define authentication, authorization, and error output

- `401 Unauthorized`: no valid authentication;
- `403 Forbidden`: authenticated but not authorized;
- `404 Not Found`: absent resource, or existence hidden by anti-enumeration policy;
- `409 Conflict`: business-state or idempotency conflict;
- `412 Precondition Failed`: stale revision;
- `422 Unprocessable Content`: structurally valid command that fails domain validation;
- `428 Precondition Required`: missing required concurrency precondition;
- every 4xx and 5xx response uses ProblemDetails with a stable `code`, `traceId`, and safe details;
- 5xx output must not expose stacks, SQL, prompts, tool payloads, or provider responses.

### 7. Define input and approval expiry

- InputRequest and ApprovalRequest receive a server-generated `expiresAt`;
- expiry is driven by a durable timer, not an in-memory HTTP timer;
- submitting after expiry returns `409 REQUEST_EXPIRED` and cannot revive the request;
- expired input moves the run to `failed` with `INPUT_EXPIRED`; an explicit retry creates a new request;
- expired approval moves the run to `failed` with `APPROVAL_EXPIRED` and cannot produce Apply Authorization;
- retry creates a new request ID, expiry, and resource revision; an old response cannot satisfy the new request.

### 8. Define SSE cursor, retention, and backpressure

- the durable SSE cursor references only the public AgentEvent sequence from ADR-020;
- `Last-Event-ID` is the reconnection entry point;
- a cursor older than the retention window returns `410 Gone` and a link to retrieve the current resource snapshot;
- AgentStreamDelta does not promise replay;
- when a slow consumer exceeds the server buffer, the server disconnects it after recording the last successfully sent durable cursor;
- buffer size, retention duration, and connection limits are deployment settings, not contract constants, but deployments must declare defaults and hard limits.

### 9. Remove obsolete API shapes

The refactor must delete endpoints and generated models that accept complete AgentRun or unsigned caller-owned ApplyAuthorization documents. Do not retain deprecated endpoints, conversion middleware, shadow writes, or compatibility flags.

## Acceptance evidence

- OpenAPI contains no write operation that accepts complete AgentRun or caller-owned ApplyAuthorization resources;
- no first-party API model carries a release-generation suffix or version field;
- obsolete endpoints, generated models, and fallback parsers are removed;
- attempts to set server-owned fields are rejected;
- JWS payload, protected-header allowlist, JCS bytes, and signature fixtures pass;
- `If-Match` success, missing, stale, and business-conflict paths are tested;
- bodyless digests are identical in Go and TypeScript;
- ProblemDetails behavior is consistent for all listed status families;
- input/approval expiry, retry, and old-response replay tests pass;
- SSE reconnect, expired cursor, and slow-consumer tests pass.

## Consequences

### Benefits

- Callers can submit only authorized business intent.
- Signing ownership and the verifiable authorization carrier are explicit.
- Idempotency, concurrency, errors, expiry, and stream recovery are testable across implementations.

### Costs

- OpenAPI, generated SDKs, and every current caller must be refactored together.
- Clients must retain ETags and handle precondition failures.
- Durable expiry timers and SSE retention behavior must be implemented.
